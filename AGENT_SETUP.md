# Агенту: повне встановлення й налаштування ALIVE

**Результат:** учасник читає й редагує ALIVE в Obsidian, бачить стан своєї копії в панелі Git і отримує прийняті оновлення автоматично. Агент готує правки окремими гілками; людина приймає їх у спільну версію.

Виконуй цю інструкцію на **комп’ютері учасника**, який попросив підключення. Працюй українською. Спочатку перевір установлене, потім установи відсутнє, налаштуй проєкт і перевір результат. Повторний запуск має використовувати готові налаштування й зберігати незавершену роботу.

> [!IMPORTANT]
> **Основний інтерфейс — Obsidian із плагіном Git від Vinzent.** Учаснику не потрібно регулярно натискати Fetch/Pull у GitHub Desktop. Автоматично отримуємо зміни; автоматичні коміти й відправлення правок вимкнені.

## 1. Перевір комп’ютер

Визнач ОС, її версію та архітектуру. Перевір доступ до термінала, файлової системи, браузера й GUI. Якщо агент працює лише в браузерному чаті й не має доступу до цього комп’ютера, прямо повідом це: установка ще не виконана. Допоможи підключити доступний локальний агент або дай людині лише ті дії, які ти справді не можеш виконати.

| Компонент | Навіщо | Перевірка |
| :--- | :--- | :--- |
| **Obsidian** | Вікі, PDF і робочі нотатки | Установлений застосунок; фактична версія в About |
| **Git** | Локальні версії, отримання й передача змін | `git --version` |
| **GitHub CLI — gh** | Авторизація, права, pull requests | `gh --version` |
| **Python 3.11+** | Перевірка посилань і джерел | `python3 --version` або `py -3 --version` |
| **Git — obsidian-git** | Автооновлення й панель стану в Obsidian | Settings → Community plugins |
| **GitHub Desktop** | Додатковий візуальний Git-клієнт | Не обов’язковий для роботи через плагін; установлення описано нижче |

Перевір також наявну папку Alive і її Git-стан. Не перевстановлюй справні програми, не змінюй чужі сховища Obsidian й не замінюй налаштований агент користувача іншим продуктом.

**Готово, коли:** відомі ОС, потрібні відсутні компоненти та місце майбутньої копії. Коротко повідом користувачу, що встановиш.

## 2. Установи відсутні програми

Установлюй тільки з офіційних сайтів або перевірених системних каталогів. Використовуй звичайні дозволи свого середовища. Паролі, 2FA, системний пароль і необхідні особисті підтвердження вводить користувач; після цього продовжуй роботу. Платні підписки для цієї схеми не потрібні.

### macOS

Якщо Homebrew уже доступний і підтримує цю ОС, установи **лише відсутні** компоненти відповідними командами:

```sh
brew install git
brew install gh
brew install python
brew install --cask obsidian
```

За потреби додаткового GitHub Desktop:

```sh
brew install --cask github
```

Якщо Homebrew немає, перевір підтримку поточної macOS на [офіційному сайті](https://brew.sh/). Для сумісної системи встанови його офіційним інсталятором; виконай показані ним **Next steps**, щоб команда `brew` була доступна в новому терміналі. Можна використати офіційний `.pkg`. Не оновлюй саму ОС заради цього завдання.

Альтернативи без Homebrew: [Obsidian](https://obsidian.md/download) через DMG → Applications; [GitHub CLI](https://cli.github.com/) через офіційний реліз; [Python](https://www.python.org/downloads/macos/) через офіційний інсталятор. Для системного Git за відсутності Command Line Tools виконай `xcode-select --install` і дочекайся завершення встановлення користувачем. Повний Xcode не потрібний.

[Пакет Obsidian](https://formulae.brew.sh/cask/obsidian) · [Пакет GitHub Desktop](https://formulae.brew.sh/cask/github)

### Windows

Перевір `winget --version`. Якщо WinGet відсутній, установи або онови офіційний **App Installer** через Microsoft Store. Перед установленням звір пакет командою `winget show --id ID --exact --source winget`.

Виконуй потрібні команди окремо, пропускаючи вже встановлене:

```powershell
winget install --id Git.Git --exact --source winget
winget install --id GitHub.cli --exact --source winget
winget install --id Obsidian.Obsidian --exact --source winget
winget install --id Python.Python.3.13 --exact --source winget
```

Python 3.13 тут — конкретний доступний пакет; якщо вже є робочий Python 3.11 або новіший, другий інтерпретатор не встановлюй. Після інсталяції відкрий новий термінал і повтори перевірку команд. Наявність `python.exe`, який лише відкриває Microsoft Store, не є встановленим Python.

За потреби додаткового GitHub Desktop:

```powershell
winget install --id GitHub.GitHubDesktop --exact --source winget
```

Якщо WinGet недоступний, використовуй офіційні інсталятори [Git](https://git-scm.com/downloads/win), [GitHub CLI](https://cli.github.com/), [Obsidian](https://obsidian.md/download), [Python](https://www.python.org/downloads/windows/) і, за потреби, [GitHub Desktop](https://desktop.github.com/).

[Довідка Microsoft про встановлення через WinGet](https://learn.microsoft.com/en-us/windows/package-manager/winget/install)

### Linux

Визнач дистрибутив і пакетний менеджер. Для Debian/Ubuntu установи відсутні `git` та `python3` через `apt`; для GitHub CLI використай [офіційний спосіб для цього дистрибутива](https://github.com/cli/cli/blob/trunk/docs/install_linux.md). Перевір версію Python перед запуском перевірки.

Obsidian завантаж з [офіційної сторінки](https://obsidian.md/download): `.deb` для відповідної Debian/Ubuntu-системи або AppImage для своєї архітектури. Для AppImage додай право виконання та запусти файл; якщо бракує системної залежності, установи її штатним способом дистрибутива. GitHub Desktop офіційно не підтримує Linux; у цій схемі його замінюють Git CLI й панель Git в Obsidian.

**Готово, коли:** працюють Git, gh і Python; Obsidian відкривається. Python-пакети з pip, Node.js, Docker, платний Sync і сторонні AI-плагіни для ALIVE не потрібні.

## 3. Налаштуй GitHub-авторизацію

Читання відкритого репозиторію можливе без входу. Для редагування й майбутнього приватного доступу потрібен **особистий акаунт учасника**, прийняте запрошення та право запису. Відкритий репозиторій сам по собі права запису не дає.

Перевір наявний вхід:

```sh
gh auth status --hostname github.com
```

Якщо правильний акаунт уже працює, збережи його. Інакше запусти браузерний вхід; пароль і 2FA вводить користувач:

```sh
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git --hostname github.com
gh api user --jq .login
gh api repos/esannikov/Alive --jq '{private: .private, permissions: .permissions}'
```

`permissions.push: true` підтверджує право запису на рівні репозиторію. Якщо воно false або відсутнє, підготуй локальну вікі для читання, покажи користувачу його логін і поясни, що адміністратор має запросити цей акаунт. Запрошення може прийняти лише його одержувач. Після приймання перевір права повторно.

Перевір, що gh використовує системне сховище облікових даних. Не копіюй токени в Markdown, конфіг плагіна або чат; `gh auth token` для цього процесу не потрібна. Якщо gh повідомляє про зберігання секрету відкритим текстом, налаштуй штатне сховище цієї ОС перед завершенням.

[Браузерна авторизація gh](https://cli.github.com/manual/gh_auth_login) · [Підключення облікових даних до Git](https://cli.github.com/manual/gh_auth_setup-git)

## 4. Підключи локальну копію

Обери звичайну локальну папку поза iCloud, OneDrive, Dropbox та іншими синхронізаторами. Типовий варіант — папка `Projects/Alive` у домашньому каталозі учасника.

Для **нової** копії на macOS/Linux:

```sh
ALIVE_DIR="$HOME/Projects/Alive"
mkdir -p "$HOME/Projects"
git clone https://github.com/esannikov/Alive.git "$ALIVE_DIR"
cd "$ALIVE_DIR"
```

Для **нової** копії в PowerShell:

```powershell
$AliveDir = Join-Path $env:USERPROFILE 'Projects\Alive'
New-Item -ItemType Directory -Force (Split-Path $AliveDir) | Out-Null
git clone https://github.com/esannikov/Alive.git "$AliveDir"
Set-Location "$AliveDir"
```

Якщо папка вже існує, **не виконуй клонування поверх неї**. Перевір `git status --short`, `git remote -v`, поточну гілку й локальні коміти. Переконайся, що origin веде саме на `esannikov/Alive`. У цього проєкту вже очищали історію: якщо стара копія не має спільного предка з origin/main, створи свіжу поруч, збережи незавершені правки й перенеси потрібне окремо. Стару історію назад не зливай.

Прочитай [AGENTS.md](AGENTS.md), [CONTRIBUTING.md](CONTRIBUTING.md) і [правила біблії](Bible/Rules.md). Перевір Git-авторство. Якщо ім’я або email не задані, уточни в учасника й установи **лише для цього репозиторію** через `git config --local`; для email підійде підтверджена GitHub noreply-адреса з налаштувань його акаунта.

Налаштуй приймання тільки послідовних оновлень:

```sh
git config --local pull.ff only
git config --local merge.ff only
git config --local push.default simple
git config --local remote.pushDefault origin
```

Параметри pull.ff та merge.ff потрібні: плагін виконує `fetch` і `merge` окремо. За розходження історії Git має зупинитися, а не створювати автоматичне злиття. У гілці main для читання має бути налаштовано upstream origin/main. push.default=simple та remote.pushDefault=origin задають однозначний стандартний напрямок ручного відправлення; у робочої гілки пізніше має бути власний однойменний upstream.

## 5. Відкрий проєкт в Obsidian

1. Запусти Obsidian і вибери **Open folder as vault / Відкрити папку як сховище**.
2. Вибери клоновану папку Alive. Якщо людина має інші сховища, збережи їхні налаштування.
3. Відкрий [командний дашборд](TEAM_DASHBOARD.md), додай його до **Bookmarks**.
4. Перевір відкриття [персонажів](Bible/Characters.md), [світу](Bible/World.md), [карти біблії](Bible/README.md) та [PDF роману](Sources/ALIVE.pdf).
5. Для читання ввімкни Reading view. У Files and links увімкни оновлення внутрішніх посилань; для нових посилань використовуй Markdown і відносні шляхи.

Локальні налаштування Obsidian і плагіни зберігаються в `.obsidian` та не передаються через Git. Зразок файлових налаштувань — [config/obsidian-vault.json](config/obsidian-vault.json); застосуй його лише до нового неналаштованого сховища, зберігаючи особисті параметри вже наявного.

**Готово, коли:** сховище відкрите, внутрішні переходи працюють, PDF читається. Якщо GUI недоступний агенту, попроси людину відкрити сховище й підтвердити ці конкретні дії; не оголошуй GUI-перевірку виконаною лише за наявністю файлів.

## 6. Установи й налаштуй плагін Git

> [!IMPORTANT]
> Установлюй плагін **Git**, автор **Vinzent**, ID **obsidian-git**. Це запис з офіційного каталогу Community plugins. Налаштування нижче перевірені для версії **2.41.1**; вона потребує Obsidian **1.13.0+**. Для іншої версії звір назви й поведінку параметрів.

### Установлення

У **сховищі Alive** відкрий **Settings → Community plugins → Browse**, знайди Git від Vinzent, натисни **Install**, потім **Enable**. Якщо Restricted mode заважає, пройди штатний діалог дозволу сторонніх плагінів за правилами свого середовища та підтвердженнями користувача.

Якщо встановлюєш файлами, спочатку перевір офіційний запис ID у [каталозі Obsidian](https://github.com/obsidianmd/obsidian-releases/blob/master/community-plugins.json), потім отримай `main.js`, `manifest.json` і `styles.css` **з одного сумісного офіційного релізу** [Vinzent03/obsidian-git](https://github.com/Vinzent03/obsidian-git/releases). Розмісти їх у `.obsidian/plugins/obsidian-git`, після чого ввімкни плагін у UI. Не змінюй файли конфігурації, які відкритий Obsidian зараз може перезаписати; використай UI або закрий саме це сховище перед записом.

### Профіль автоотримання та ручної відправки

| Параметр Git | Значення |
| :--- | :--- |
| Auto pull interval | **5 хвилин** |
| Pull on startup | **Увімкнено** |
| Auto commit / commit-and-sync interval | **0 — вимкнено** |
| Auto push interval | **0 — вимкнено** |
| Push on commit-and-sync | **Увімкнено для ручної команди**; таймери комітів і push залишаються 0 |
| Pull before push | **Вимкнено**; агент окремо перевіряє основу перед передачею правок |
| Merge strategy | **Merge**; у Git уже задано `merge.ff=only` |
| Merge strategy on conflicts | **None** |
| Auto-stash changes when rebasing | **Disabled**; rebase не використовується |
| Status bar / branch / changed files | **Увімкнено** |
| Refresh source control | **Увімкнено** |
| Error notices | **Увімкнено** |

Точний JSON-профіль — [config/obsidian-git.reading.json](config/obsidian-git.reading.json). Він призначений для `.obsidian/plugins/obsidian-git/data.json`. При наявному конфігу об’єднай тільки ці параметри; збережи інші персональні поля. Після запису перезавантаж плагін або сховище й перевір значення в UI.

### Одна команда для ручної відправки

Для учасника, який сам пише в Obsidian, увімкнено **Git: Commit-and-sync**. Команда вручну створює commit і відправляє його в upstream поточної робочої гілки. Вона працює також при призупинених автоматичних операціях. Окремо виконувати staging, Commit і Push для звичайної цілісної правки не потрібно.

До передачі цього режиму учаснику агент має підготувати **окрему робочу гілку**, налаштувати її власний однойменний upstream на origin і перевірити право запису. Точні команди та перевірка — [підготовка робочої гілки](CONTRIBUTING.md#1-підготувати-робочу-гілку). Цей крок виконується на початку реальної правки, а не автоматично під час першого встановлення. Колега редагує текст, потім виконує **Ctrl+P / Cmd+P → Git: Commit-and-sync**. За бажанням учасника признач гарячу клавішу, попередньо перевіривши конфлікти в Settings → Hotkeys.

> [!NOTE]
> Команда включає всі поточні неігноровані зміни в папці проєкту. Використовуй її для однієї завершеної правки у підготовленій робочій гілці. Команда не створює PR, не запускає validate.py та не приймає зміни до main. Агент або редактор окремо перевіряє саме відправлену гілку, створює PR, а людина приймає його. Повідомлення про успішний commit без успішного push ще не означає передачу правки.

Якщо під час відправлення Git повідомляє про відсутній upstream, право запису або розходження версій, збережений локальний commit лишається на комп’ютері. Агент усуває конкретну причину; force-push і автоматичне відкидання чужих змін не використовуються.

### Панель стану

Відкрий командну палітру Obsidian — **Ctrl+P / Cmd+P** — і виконай **Git: Open source control view**. Залиш панель праворуч. Увімкнені рядок стану й назва гілки показуватимуть поточну копію та локальні зміни. **Git: Open history view** відкриває журнал версій.

Плагін працює, поки відкрите відповідне сховище Obsidian. Це не окремий фоновий сервіс: при закритому застосунку таймер не працює; наступний запуск отримує оновлення.

### Під час редактури

Плагін отримує **upstream поточної гілки**, а не завжди main. Він не має окремої гарантії «оновлювати тільки чисту main». Тому використовуй два явні режими:

- **Читання:** main, без незавершеної редактури; автоматичне отримання увімкнене.
- **Редактура:** спочатку **Git: Pause/Resume automatic routines** → дочекайся повідомлення **Paused automatic routines**; потім створи окрему гілку й редагуй. Після погодження, завершення локальної роботи й повернення до чистої main виконай цю команду знову й перевір повідомлення **Resumed automatic routines**.

Це перемикач: перевір фактичне повідомлення, щоб випадково не відновити автоматику замість паузи. Автоматичні коміти й push лишаються вимкненими в обох режимах. Конфлікт або розходження історії розбирає агент із людиною; стратегії `ours`, `theirs`, reset і автоматичне відкидання правок не використовуються.

## 7. Перевір готовність

Виконай у папці Alive:

```sh
git remote get-url origin
git status --short
git branch --show-current
git config --local --get pull.ff
git config --local --get merge.ff
gh api repos/esannikov/Alive --jq '{private: .private, permissions: .permissions}'
```

Запусти перевірку документів фактично встановленим Python:

```sh
python3 scripts/validate.py
```

На Windows, якщо використовується launcher:

```powershell
py -3 scripts/validate.py
```

Перевір у самому Obsidian:

1. Git-плагін увімкнений; панель Source Control відкривається й показує гілку.
2. **Git: Pull** завершується без помилки — через ті самі облікові дані, які плагін використовуватиме автоматично.
3. Профіль показує інтервал 5, startup pull увімкнений, auto commit і auto push — 0; Push on commit-and-sync увімкнений. Перевір значення в самому плагіні, а не тільки в JSON-шаблоні.
4. Дочекайся одного автоматичного циклу або перезапусти саме сховище й перевір startup pull. Не підміняй цю перевірку успішним pull у терміналі.
5. Перевір паузу й відновлення за повідомленнями. Залиш читальну main у режимі відновленої автоматики, якщо немає незавершених змін.
6. `permissions.push` окремо показує право запису на рівні репозиторію. Установка плагіна не надає цього права. Це ще не перевірка повного циклу Commit-and-sync → PR → merge; її виконайте на першій погодженій реальній правці.

Пробні коміти, гілки та pull requests для перевірки доступу не потрібні. Якщо потрібен повний командний тест, окремо погодьте одну реальну невелику правку й пройдіть її за CONTRIBUTING.md.

## 8. Передай учаснику готове робоче місце

Залиш відкритими **TEAM_DASHBOARD.md** і панель **Git Source Control**, main без незавершених правок і відновлену автоматику. Якщо цього не досягнуто, передай точний стан, а не позначку «готово». Покажи три дії:

1. **Читати:** відкривати дашборд і потрібний розділ; прийняті оновлення надходитимуть автоматично.
2. **Редагувати:** сказати агенту «Почнімо правку» — агент ставить автоматику на паузу й готує окрему гілку.
3. **Передати правки:** у підготовленій робочій гілці виконати **Git: Commit-and-sync** або сказати агенту «Покажи зміни й підготуй запит». Після приймання повернутися до main й відновити автоматику.

Звіт залиш у чаті користувача, без токенів. Укажи: ОС; установлені або вже наявні програми й версії; шлях до копії; GitHub-логін; підтверджені права читання/запису; версію Git-плагіна; результати перевірки документів, GUI та автоматичного pull; усе, що ще очікує дії людини.

**Статус «готово до читання»** означає, що локальна вікі й отримання змін перевірені. **«Можна починати редактуру з агентом»** додатково потребує права запису. **«Ручна відправка готова»** для конкретного завдання потребує перевіреної робочої гілки та її upstream. Для всього командного циклу окремо зафіксуй результат першої реальної правки. Якщо перевірка недоступна або не завершена — назви її прямо й продовж решту доступного налаштування.

## Після повернення приватного доступу

Не змінюй видимість репозиторію самостійно. Перед закриттям адміністратор має переконатися, що запрошення прийняті, а кожен учасник авторизований своїм акаунтом. Після закриття повторно перевір `git fetch origin` і Pull у плагіні. Сам факт попереднього публічного клонування приватного доступу не гарантує; наявна локальна копія залишається на комп’ютері.
