# Типаж і кадр — контракт даних

[Дашборд](README.md) · [Реєстр типажів](identity_variants.json) · [Публічний JSON](https://esannikov.github.io/Alive/World/identity-variants.json)

## Два окремі ідентифікатори

- `code`, наприклад `emma038`, називає конкретне незмінне зображення.
- `variant_id`, наприклад `emma-type-009`, називає конкретний типаж одного персонажа. Його ракурси, міміка, вікові уточнення та кольорові версії можуть мати різні коди зображень.

Літери А/Б/В — вибір продюсерів, а не постійний ID. Вони не повинні залежати від порядку кадрів, номера першого видимого зображення або обкладинки галереї. Нова обкладинка не створює новий типаж.

## Що читати агенту трекера

Публічний файл `World/identity-variants.json` — звичайний JSON, без виконання JavaScript. Поле `schema_version` наразі дорівнює 1; `selection_unit` — `identity_variant`.

```json
{
  "character": "emma",
  "asset_code": "emma038",
  "variant_id": "emma-type-009",
  "selection": "A"
}
```

Це приклад структури вибору для інтеграції, не нове рішення продюсера й не чинна сигнатура MCP `decide`.

1. Знайти `assets[asset_code].identity_variant_ids[character]`.
2. Якщо ID є, вибір типажу прив’язувати до цього ID. Усі його `active_asset_codes` показувати як кадри одного обраного типажу.
3. Якщо є `assets[asset_code].review_required[character]`, автоматичне зіставлення не робити: спершу визначити, яке саме обличчя показане.
4. Оцінку конкретного кадру зберігати окремо. Відхилення невдалого ракурсу не дорівнює відхиленню всього типажу; вибір типажу не означає приймання якості кожного його кадру.
5. `member_codes` містить і джерела/архівні похідні. Для поточного показу використовувати `active_asset_codes`; архівні кадри автоматично не повертати в галерею.

У `World/data.js` ті самі зв’язки доступні як `identityVariants`, а в кожному зображенні — `identityVariantIds`, `identityReviewRequired` та `identityRoles`.

## Перевірені приклади

- `emma027`, `emma028`, `emma033`, `emma037`, `emma038` → `emma-type-009`. Це ланцюг від `emma009` через вікові правки 012/013 та подальші редакції. Вкладення для 037 зіставлено з масштабованим `emma012` за пікселями й візуально.
- `emma023`, `emma024`, `emma025` — три різні типажі 020/021/022; спільний опис у промпті не об’єднує їх.
- `tais053`, `tais057`, `tais060`, `tais061` → `tais-type-053` (А). `tais059` → окремий `tais-type-059` (Б): пряме рішення продюсерів важливіше спільного референсу.
- `fedor009`, `fedor031`, `fedor033` → `fedor-type-009`.
- `nitka007` і `nitka008` → `nitka-type-003`.
- `kolka033–036` → `kolka-type-015`: чотири зачіски однієї основи.
- Спільний кадр `romik007` має два зв’язки: `romik-type-002` для Ромика і `vovik-type-007` для Вовика. Подібність хлопців не робить їх одним персонажем або одним типажем.

## Кадри, які потребують зіставлення

`emma036` — костюмний лист із номером; джерельний типаж не зафіксований однозначно. `ira007` та `senka007` — ансамблеві генерації, для яких попередня документація прямо залишала перевірку схожості відкритою. Вони залишаються видимими й мають позначку, а не довільно приєднуються до схожого портрета.

## Як підтримувати реєстр

Джерело — `Production/Dashboard/identity_variants.json`. Новий незалежний кастинг отримує новий ID. Редакція, яка явно зберігає обличчя, додається до наявного типажу. Для спільної сцени задається зв’язок окремо для кожного персонажа. Непідтверджену схожість позначати `review_required`.

Не перенумеровувати ID після перенесення кадру в резерв. Поле `derived_from` описує походження генерації й саме по собі не доводить тотожності типажу. Попередні коди зображень, коментарі, реакції та затвердження зберігаються.

Перевірки: `python3 scripts/validate_identity_variants.py`, `python3 scripts/validate_world.py`; інтерактивний сценарій — `scripts/test_identity_variants.cjs`.

Інтеграція вибору А/Б/В на стороні стороннього трекера має читати цей контракт. Цей пакет не змінює алгоритм затверджень трекера й не переносить старі реакції Giscus між зображеннями.
