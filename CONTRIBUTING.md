# Правки й синхронізація

## Перед початком

Перевір `git status --short`, поточну гілку та remote. Якщо є незавершені або чужі правки, спершу збережи й узгодь їх. Не застосовуй `reset --hard`, видалення файлів або force-push для автоматичного усунення конфліктів.

Для чистої копії й нового завдання:

```sh
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c codex/short-task-name
```

`short-task-name` заміни короткою назвою завдання. Префікс позначає робочу гілку й не вимагає конкретного AI-продукту. Запиши SHA основи через `git rev-parse HEAD`.

## Підготовка зміни

1. Редагуй потрібні файли Bible; зберігай відносні Markdown-посилання.
2. Для нової творчої пропозиції вкажи статус і джерело. Прочитай пов’язані сторінки, які можуть суперечити зміні.
3. Запусти `python3 scripts/validate.py`, переглянь `git diff --check` і сам `git diff`.
4. Додай до commit лише файли свого завдання через `git add <конкретні-файли>`; перевір `git diff --cached` перед commit.
5. Зроби commit із предметним поясненням. За дорученням користувача відправ гілку: `git push -u origin HEAD`.
6. Відкрий pull request до main. Через CLI: `gh pr create --base main`; або кнопку **Create Pull Request** у GitHub Desktop. Для багаторядкового опису агент використовує файл і `--body-file`.

## Що писати в запиті

Що змінилося, навіщо, джерела, чи є нові факти/дизайни, які розділи зачеплено, результат перевірки, що саме має вирішити людина. Поки рішення не прийняте, познач запит як чернетку (Draft), якщо це незавершена пропозиція.

## Перегляд і приймання

Технічний доступ надає адміністратор репозиторію. Учасники команди можуть пропонувати та обговорювати зміни після приймання запрошень. Творчі повноваження узгоджуються командою; ця інструкція не призначає їм нових посад.

Перед злиттям звір зміни з поточним origin/main. Якщо основа змінилася, онови робочу гілку й повтори перевірку; змістові суперечності вирішує людина. Погоджені зміни світу фіксуй у Decisions із посиланням на pull request. Після злиття інші учасники оновлюють main у чистій локальній копії.

Станом на 09.10.2026 GitHub відхилив увімкнення захисту main для приватного репозиторію: ця можливість потребує GitHub Pro або іншого відповідного платного плану. Підписку не змінено. Учасник із правом запису технічно може змінити main напряму; працюємо через окремі гілки й людський перегляд.

Правило роботи через pull request діє як командний порядок. Стан технічного захисту main перевіряється окремо в Settings → Rules/Branches; наявність CODEOWNERS сама його не вмикає.

## Файли й доступ

Власні налаштування Obsidian, кеші, плагіни, секрети та великі медіа не коміть. Не підключай автоматичне відправлення прямо в main. Кожен агент працює через власника свого GitHub-акаунта, а не через спільний пароль. Issues і PR-коментарі читаються окремо через GitHub API/CLI або браузер.

PDF роману й документи Sources/Extracted є вхідними джерелами; скрипт перевіряє їхні SHA-256. Заміна джерела — окреме погоджене завдання з оновленням походження та похідних покажчиків.
