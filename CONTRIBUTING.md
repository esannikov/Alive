# Правки й приймання спільної версії

[Головна](README.md) · [Робоче місце](TEAM_DASHBOARD.md) · [Біблія](Bible/README.md) · [Джерела](Sources/README.md) · [Питання](Decisions/Open_Questions.md)

Це технічна процедура для агента й відповідального редактора. Людський вхід — [START_HERE.md](START_HERE.md); установлення програм — [AGENT_SETUP.md](AGENT_SETUP.md).

## Чотири стани роботи

| Стан | Гілка | Автоматичне отримання | Наступна дія |
| :--- | :--- | :--- | :--- |
| Читання | main | Увімкнене | Агент готує нове завдання |
| Редактура | Окрема робоча гілка | На паузі | Автор пише й виконує Commit-and-sync |
| На перегляді | Та сама робоча гілка | На паузі | Агент створює PR, редактор переглядає |
| Прийнято | Повернення до чистої main | Відновлене | Отримання погодженої спільної версії |

Установлення завершується режимом читання. Робочу гілку створюй, коли є конкретна правка; самостійний Commit-and-sync у main не є робочим маршрутом команди.

## 1. Підготувати робочу гілку

Перевір локальну копію, origin і авторизацію користувача. Виконай `git status --short` та перевір поточну гілку. Збережи незавершені або чужі зміни; без згоди автора не застосовуй reset, discard чи force-push.

В Obsidian виконай **Git: Pause/Resume automatic routines** й перевір повідомлення **Paused automatic routines**. Якщо автоматичні операції вже на паузі, не перемикай їх повторно. За недоступності GUI попроси користувача виконати саме цей крок.

Для чистої копії:

```sh
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c codex/LOGIN-TOPIC
git push -u origin HEAD
```

`codex/LOGIN-TOPIC` — позначка: перед виконанням підстав перевірений логін і коротку тему. Якщо така гілка вже є, перевір її призначення й незавершену роботу; не замінюй її автоматично. Початковий push створює гілку з чинною базою, щоб ручний Commit-and-sync уже мав куди відправляти наступні правки.

Перевір:

```sh
git branch --show-current
git rev-parse --abbrev-ref --symbolic-full-name '@{upstream}'
git rev-parse HEAD
```

У результаті мають бути робоча гілка та її **однойменна** гілка на origin, а не origin/main. Запиши SHA основи. Якщо права запису або upstream не налаштовані, не передавай учаснику кнопку як готовий спосіб відправлення.

## 2. Редагувати й відправити

Автор може писати самостійно в Obsidian. Для цілісної правки команда **Git: Commit-and-sync** створює commit і відправляє його в поточну робочу гілку. Автоматичні коміти та push за таймером вимкнені; пауза автоматики не блокує ручну команду.

Команда включає всі неігноровані зміни в робочій папці. Вибіркову передачу агент робить через staging конкретних файлів, перевірку `git diff --cached` і звичайний commit/push. Для одного завдання не змішуй непов’язані правки або особисті нотатки.

> [!IMPORTANT]
> **Commit-and-sync не створює pull request, не запускає перевірку біблії та не виконує merge до main.** Після успішного відправлення агент або редактор має виконати наступний крок.

Якщо push відхилено, локальний commit залишається в копії. Перевір причину: доступ, upstream, мережа, нові зміни на сервері чи конфлікт. Не підміняй усунення причини примусовим push.

## 3. Створити запит на перегляд

У правильній робочій гілці перевір зміни й джерела:

```sh
python3 scripts/validate.py
git diff --check
git diff origin/main...HEAD
```

На Windows можна використати `py -3 scripts/validate.py`, якщо це перевірений Python launcher. Якщо потрібні виправлення, внеси їх окремо, перевір і відправ.

Спочатку перевір наявність PR через `gh pr view`: нові коміти вже відкритого PR оновлюють той самий запит. Закритий або вже прийнятий PR не використовується для нового завдання: підготуй нову гілку й новий запит. Якщо його немає, створи PR до main через `gh pr create --base main --head codex/LOGIN-TOPIC`. Для багаторядкового опису агент готує файл і передає його через `--body-file`. У браузері — **Compare & pull request → Create pull request**.

В описі вкажи: що й навіщо змінилося, джерела, нові творчі пропозиції, зачеплені розділи, результат перевірок і питання до людини. Зміни, які ще не готові до приймання, познач як Draft.

Якщо PR створює відповідальний редактор зі своєї копії, він має перевіряти **відправлену гілку автора**, а не лише свою поточну main. Отримай її через fetch і переглянь у чистій окремій робочій копії або checkout, зберігши власні незавершені зміни.

## 4. Прийняти й повернути автора до читання

Відповідальний редактор переглядає **Files changed**, коментарі та результати перевірок. Нові факти світу й зміни дизайну приймає людина. Після погодження виконай merge у main; погоджені творчі рішення зафіксуй за [правилами журналу](Decisions/README.md).

Перед поверненням автора перевір, що PR справді має стан **MERGED**, у робочій гілці немає невідправлених комітів, а в папці — незбережених або незакомічених правок. Тільки після цього:

```sh
git fetch origin
git switch main
git pull --ff-only origin main
```

Перевір чистий Git-стан, main і відповідність origin/main. Віднови автоматику командою **Git: Pause/Resume automatic routines** та перевір повідомлення **Resumed automatic routines**. Після цього автор і інші читачі отримуватимуть нові прийняті зміни.

Поки учасник залишається у робочій гілці з паузою, його копія не переходить на нову main автоматично. Гілку іншого учасника й його локальні файли не видаляй без відповідного доручення.

## Доступ і локальні налаштування

Поточну видимість і права визначає GitHub. На перевірці 09.10.2026 репозиторій публічний для читання, а примусовий захист main не ввімкнений. Робота через гілки й PR — командний порядок; наявність CODEOWNERS сама не блокує прямий запис.

Кожен користується власним акаунтом. Для запису й майбутнього приватного доступу потрібне прийняте запрошення. Зміна видимості, запрошення або поширення матеріалів потребують окремого доручення.

`.obsidian` з особистими налаштуваннями й плагінами ігнорується Git. Зміна шаблону в config/ не переналаштовує вже встановлений плагін автоматично: агент має застосувати профіль у кожному сховищі й перевірити UI. Основне джерело роману — Sources/ALIVE.pdf; зміни джерел виконуються окремим погодженим завданням.
